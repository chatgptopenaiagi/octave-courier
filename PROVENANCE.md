# Source provenance

Octave Courier adapts an integration developed for the project originator's local
engineering environment. The originator explicitly authorised extraction,
standalone engineering and publication of the reusable integration software.

The relevant starting components were `python_bridge.py`, `bridge_worker.m`, a
representative mathematical verification script and a PowerShell script launcher.
They supplied the finite-real matrix contract, shape-preserving JSON exchange,
bounded child execution and independent numerical-check patterns.

For this public product, runtime discovery, portable resource handling, API and
CLI boundaries, fixed demonstrations, packaging, examples and release tests were
developed in an independent workspace. Workstation configuration, credentials,
private source repositories and engineering databases are not part of the product.

The scoped source review found no third-party copyright/license headers in those
starting integration files, and no governing `LICENSE` or `COPYING` file in their
relevant local parent directories. The project originator's authorisation covers
the new integration release. This statement is limited to the files actually
extracted; it is not a license conclusion about unrelated engineering projects.

No GNU Octave implementation source was copied into this project. The included
`.m` worker and examples are integration/application code that invokes Octave
operations. GNU Octave remains a separate dependency with its own copyright and
license. The project's MIT license does not replace dependency licenses.

The release manifest identifies the public source commit used to build artifacts.
Private local preservation records are kept outside public source archives.
See [third-party notices](THIRD-PARTY-NOTICES.md) for runtime and build-tool distinctions.
